# Git 功能与使用体验审查

日期：2026-11-07。对象：当前 Overleaf GitSync 前后端，以及本地 18081 页面。对照产品是 Venues，不是 Vimium。

## 结论

Git 已具备相当多的同步、安全检查和恢复机制，但用户操作仍按内部执行阶段组织。用户需要理解 preview、snapshot、application、reconcile，才能完成本应直接的“看修改、保存版本、同步、找回文件”。当前主要缺口是操作组织、持续状态展示和常见任务支持；单纯增大按钮、加图标不会解决。

这次没有修改产品代码、用户项目、Git 绑定或远端仓库。所有新增文件均在 `docs/git-review/`。已有未提交改动保持原样。

证据级别：**复现**指本轮隔离测试观察到；**代码确认**指当前实现可直接确定；**界面观察**指本轮本地浏览器只读查看；**待验证**指尚不能判断是否存在错误。以下 P0/P1/P2 是建议实施顺序，并不表示每项都是安全漏洞。

## 一、最值得先处理的问题

### 1. P0：后台检查远端会清空手动选中的文件【复现】

操作：进入 Changes，勾选 main.tex，等待周期远端检查。即使远端没有变化，成功检查后选中状态变为 false。

原因链：

- `git-sync-panel.tsx:297` 的 checksPaused 没有包含 manualSelection；自动推送的 blocked 却包含它（287）。
- `use-remote-checks.ts:17` 每 60 秒运行检查；refreshRemote 切换全局 busy（panel:192）。
- panel:405 将 busy 传入 PushControls.disabled。
- `push-controls.tsx:130` 把 disabled 反向用于 LocalChanges.active。
- `local-changes.tsx:24` 在 active 恢复后重新加载并清空 selected、当前 diff 和选择回调。

影响：用户选择文件和阅读 diff 的过程被后台工作打断。没有证据表明此问题会删除文件，但会造成重复操作，并让用户误以为选择未生效。切换页面后也会触发 active 重载，需一起检验。

建议：远端后台检查使用独立 loading 状态；不要用全局 busy 控制本地面板生命周期。选中路径按文件快照校验后保留，真正失效时说明原因。先增加“远端无变化时保留选择与 diff”的回归测试。

本轮 `selection-reproduction.cjs` 是**证明现有缺陷**的测试，其通过条件是观察到选择丢失；它不是修复验收测试。

### 2. P1：默认进入 Settings，用户第一眼看不到自己的工作【界面观察、代码确认】

`git-sync-panel.tsx:90` 固定默认 Settings。当前实际页面约 559px 宽，几乎整个首屏都是凭据、同步说明和自动同步配置；“Open Changes”在下方。仓库、分支、检查时间只集中在设置页，其他页没有完整的常驻概览。

建议：已连接时默认 Changes；首次连接才进入连接引导。顶部常驻仓库名、当前分支、连接状态、最近成功检查时间。设置作为次级入口。对“未检查、已同步、远端更新、冲突、执行中、结果待确认”分别显示状态，不能把旧缓存等同于最新远端状态。

### 3. P1：一次提交被拆成多次审阅，且顺序与用户习惯相反【代码确认】

`push-controls.tsx:119–145` 先显示提交说明和 Prepare commit review，再显示选文件列表；准备快照后又出现文件列表、diff、确认复选框和 Push reviewed commit。

用户路径是：Changes → Local changes → 选择文件/查看差异 → 填说明 → Prepare → 再次查看快照 → 勾确认 → Push。底层保留不可变快照是正确的，但两套相近列表与技术术语增加认知负担。

建议：文件列表与 diff 在上，提交说明与“提交并推送”在下；内部仍准备不可变快照、校验版本和远端 head。正常情况下用一个连续流程；只在快照已变化、危险删除、冲突或远端权限限制时展示有具体内容的确认。不能为了减少点击而去掉并发校验。

现有“prepared commit”不等于用户可管理的“仅本地提交”功能。界面没有独立的本地提交队列、稍后统一推送流程，应明确补齐或明确命名当前功能。

### 4. P1：有远端更新时，连本地修改都难以查看【代码确认】

`git-sync-panel.tsx:400` 在 initial-review 或 hasKnownRemoteChanges 时用提示替换本地提交组件；`GitPushPreparation.mjs:112` 的 changes 接口也拒绝远端与基线不一致的请求。

阻止基于旧 head 推送合理；阻止查看自己的改动则使用户更难判断怎么合并。当前首次同步页面实际也呈现这个状态。

建议：把“查看本地相对基线的修改”和“允许准备提交”分开。本地修改始终可读，远端更新另列，推送受条件控制。首次连接给出双方文件摘要和差异数量，再进入审阅。

### 5. P1：历史能够看，却难以找、比较和恢复【界面观察、代码确认】

- `git-sync.css:304` 隐藏侧栏的时间和短 hash；实际列表主要为消息与作者。
- `GitSyncController.mjs:199` 请求最近 100 条；panel 的 truncated 提示没有继续加载入口。
- `commit-details.tsx` 提供逐文件历史 diff，但没有恢复文件、还原一次提交、任意版本比较入口。
- 缺少按文件、分支、作者或关键词查历史的 UI。
- 自动同步消息固定为时间戳（`automatic-sync.ts:48`）；实际历史中多个条目叫 Auto-sync web edits，很难判断改了什么。

建议：行内显示短摘要、作者、相对时间、分支标记；选中后展示细节。先实现文件历史、搜索/分页、比较与“恢复为新修改”，保留旧历史。恢复后仍走普通提交审阅，不直接 reset/强推。

### 6. P1：分支功能藏在 Incoming & merge，创建分支还依赖提交【代码确认】

当前分支不是统一的分支切换入口；切换与合并控件放在 Incoming & merge 内。新分支输入位于提交表单的折叠项，准备按钮要求选中文件或待完成合并。没有普通的“当前内容不变，只创建分支”入口。

建议：顶部一个分支选择器，内含切换和创建；分支管理展示当前分支、远端分支与相对状态。合并作为明确动作，显示“将 source 合并到 destination”。分支删除/改名可后续增加；不要先上 force push、rebase 等高风险复杂操作。

### 7. P1：冲突处理需要用户自行拼接整份文件【代码确认】

`conflict-controls.tsx:49–115` 提供整文件保留 Web、保留仓库、编辑整份结果、删除，以及普通 textarea。base/web/remote 版本在其他折叠块里查看。没有逐冲突块导航、左右对照或逐块接受操作。

对长 LaTeX 文件，这比有结构的冲突编辑器费力，也容易误选整份版本。未保存编辑主要在 React 状态中；该模块没有刷新前拦截或草稿持久化，刷新丢失冲突草稿需要单独浏览器验证。

建议：复用现有代码编辑器，左右显示 Web/Repository，中间或下方显示结果；按冲突块选择，显示剩余冲突数。未保存草稿应提示并支持恢复；不能仅靠“Save conflict decision”要求用户理解内部状态。

### 8. P1：异常恢复能力存在，但让用户承担过多内部判断【代码确认】

`application-controls.tsx:104–111` 暴露 Check application status、Verify unconfirmed write、Continue interrupted asset/creation/deletion、Continue remaining changes、Stop remaining changes 等动作。后端把写入结果不确定与未执行区分开是必要的，用户却不应根据内部操作类型挑恢复按钮。

建议：统一操作状态区回答三件事：“已经完成多少、哪些尚未完成、现在可以安全做什么”。正常只提供一个推荐恢复动作和一个次级动作，技术细节折叠。对停止明确写“保留已完成的 N 个文件，停止剩余 M 个”；停止不应被误认为完整撤销。结果未知时先查询原操作，禁止把重新执行作为默认重试。

## 二、功能完整性：当前有与需要补的

| 用户任务 | 当前状态 | 建议 |
|---|---|---|
| 连接已有远端 | HTTPS URL、分支、个人 token；有凭据隔离 | 校验/错误分层、默认分支、重连和更换远端流程 |
| 连接空仓库 | branch picker 提示先在外部建立首个提交 | 提供初始化/首次发布引导 |
| 看本地修改 | 逐文件选择、文本 diff | 始终可读；文件树、过滤、增删行统计 |
| 提交并推送 | 不可变快照、选择文件、受保护推送 | 缩短交互链；清晰区分准备、提交、推送 |
| 只提交不推送 | 没有独立可用的用户流程 | 支持离线/阶段性版本，展示待推送提交 |
| 查看远端更新 | 手动/定时 fetch、incoming review | 顶部状态与数量；查看不阻断本地阅读 |
| 切换/合并分支 | 有预览、应用与合并父提交处理 | 独立、可发现的入口和清晰目标分支 |
| 暂存部分代码 | 目前按文件选择 | 后续支持按 hunk 选择；避免首先扩展到逐行复杂度 |
| 暂存未完成工作 | 没有独立 stash 用户流程 | 可先做命名草稿/安全快照，明确与 Git stash 的区别 |
| 恢复历史文件 | 可以查看，缺恢复入口 | 优先支持恢复为当前修改，展示 diff 再确认 |
| 二进制 | 后端有二进制快照/处理；前端主要说明无法文本 diff | 图片预览、PDF 信息、大小变化；不能误报为全面不支持二进制 |
| Git LFS/submodule/symlink | Reader 明确阻止同步处理 | 预检查列出不支持对象；是否实现按论文项目需求决定 |
| 仓库断开/替换 | 当前组件/路由无完整用户流程 | 保留项目文件与审计记录，明确处理旧凭据/基线 |
| 跨浏览器同步偏好 | 自动同步偏好存在 localStorage | 评估按用户+项目+仓库保存；避免多个浏览器重复调度 |

URL 校验限制在允许 host 的 `https://host/owner/repo`（`GitRemoteTransport.mjs:8–34`）。SSH URL、自托管 host、GitLab 多层 group 路径不能假定支持。浏览器本轮确认已有 Gitee 绑定，因此不能再沿用旧文档的“只做了 GitHub 雏形”结论。

## 三、容易漏掉的论文协作场景

这些是需要明确产品规则和增加验证的清单，不是已确认故障：

1. **多人同时编辑**：自动同步当前选择所有变化文件（automatic-sync.ts:49），不只是操作者本人编辑。谁允许开启、提交署名如何解释、他人未完成内容是否进入提交，必须说明。
2. **协作者恰好更新远端**：保留 lease/head 校验；拒绝后保留提交说明、选中文件和已准备快照，提供继续路径。
3. **网络断开/超时**：区分“没有发送”“发送后结果未知”“已成功但本地缓存未更新”。同一个按钮不能全部叫 Retry。
4. **Token 过期、只读权限、保护分支**：错误要指向具体原因和可执行动作，避免一律提示检查网络。
5. **首次连接两个不同历史的项目**：明确哪些是新增、哪些会覆盖；不要默默把其中一边当权威。
6. **文件改名与移动**：历史 Reader 使用 --no-renames，当前会以删/增呈现。需要检测或至少提示可能改名，避免用户误判为内容消失。
7. **图片、PDF、模板和生成文件**：区分源材料与编译产物；审查 .gitignore 行为并提供不提交生成文件的设置，不能假定当前已经正确过滤。
8. **有批注/修订的文档**：Git 内容恢复与 Overleaf 批注历史是不同对象；在删除、覆盖、历史恢复中定义保留策略。
9. **远端分支删除/改名、仓库搬迁**：保留本地项目和待同步内容，给重新绑定入口。
10. **大项目和长历史**：测试快照耗时、分支数、文件数、超大文件与历史分页；当前检查耗时尚未测量，不将其直接判定为性能缺陷。
11. **关闭浏览器**：当前自动同步靠页面定时器，不是服务端后台任务；关页面后停止，且设置按浏览器保存。文案已有说明，但入口名称仍应避免让人误认为持续云端备份。
12. **只读项目成员与权限变化**：写入前后重新授权已有部分实现；需要覆盖打开页面后权限撤销、项目转移、凭据更换等实际流程。
13. **未发送的 prepared 快照**：保留 ref 有利于恢复，但应有可见的未完成操作与保留/清理政策；本轮未验证长期存储增长。
14. **键盘与窄屏**：分支搜索、文件导航、焦点恢复、加载状态读屏提示要纳入验收，而不只测按钮存在。

## 四、建议的界面结构

```text
仓库名 ↗       当前分支 ▾       远端状态 / 最近检查       设置 ⚙
Changes (N)    History           Branches

文件树 / 搜索 / 勾选      │  选中文件的差异
新增 / 修改 / 删除        │  Web 与基线，或本次合并结果
                         │  可放大查看
─────────────────────────┴─────────────────────
提交说明
已选 3 个文件                         提交并推送 ▾
                                    仅提交

统一操作状态：正在检查 / 已完成 / 需要处理冲突 / 结果待确认
```

这只是信息架构建议，尚未实施。宽侧栏可保持两栏；窄侧栏采用文件列表→diff 的可返回视图，不能把两栏硬挤进小宽度。主要状态始终可见，完整历史图和冲突编辑可展开为工作区。

Venues 值得借鉴的是：有明确对象、明确视图、当前选择可见、详情和动作就近。Git 对应对象是仓库、分支、文件和提交。不要复制 Venues 的所有筛选器；Git 的核心是让用户知道“现在在哪个分支、改了什么、下一步是什么”。图标用一致 SVG，不能替代状态文字。

## 五、实施顺序与验收标准

| 顺序 | 内容 | 可检验的完成条件 |
|---|---|---|
| P0 | 修复后台检查清空选择；保留人工操作草稿 | 无变化的 fetch、切页往返不清空选择/说明/diff；真正失效明确提示；冲突草稿刷新策略有测试 |
| P1-A | 常驻状态栏、默认 Changes、提交区重排 | 已绑定项目打开即可看改动；仓库与分支始终可见；正常提交一个连续流程，错误保留用户输入 |
| P1-B | 统一 incoming/冲突/恢复体验 | 远端有更新仍能看本地 diff；冲突可逐块解决；未知结果不会重发写操作；恢复只给适用动作 |
| P1-C | 历史查找/恢复、分支独立入口 | 搜索与分页；单文件历史恢复为新修改；无文件变化也能创建分支；切换目标与当前分支明确 |
| P2 | 仅提交、hunk、stash、ignore、二进制预览 | 逐项定义与 Overleaf 协作内容的关系，添加真实浏览器验收 |
| 暂缓 | rebase、强推、复杂 cherry-pick、完整桌面 Git 克隆 | 当前先把日常论文协作任务做顺，避免增加危险操作和界面负担 |

建议先做 P0 与 P1-A，再处理冲突/恢复、历史与分支。不能只做视觉重排，也不宜一次铺开所有 Git 命令。

## 六、本轮验证及边界

- 现有 Git 前端测试：**83 通过**。
- 精选后端隔离测试：**5 通过**，涵盖分支切换保留修改、分支合并父提交、受保护推送/未知结果查询、提交快照准备等；远端为临时本地仓库/注入测试实现。
- 新增缺陷复现：**1 通过**，证明后台检查导致选择丢失。
- 实际浏览器：1600×1000，本地 18081，查看 Settings、Changes、Commits；面板宽约559px。所有 `/git-sync/` 非 GET 请求被拦截，未 fetch、apply、push 或更换绑定。
- 截图与 UI 文本保存于本目录。实际项目处于首次同步状态，所以手动提交流程与冲突操作没有在真实项目上执行；其判断来自代码和隔离测试。
- 本轮未做真实 GitHub/Gitee 写入、网络故障注入、多人并发或全套安全审计。不把测试通过当作所有部署路径已验证。
